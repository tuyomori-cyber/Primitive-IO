1. 一番気になるのは「拡張子」の扱い

現在は、

入力ファイル名を stem、末尾の拡張子を extension として扱う。

となっていますが、「末尾の拡張子」の定義が曖昧です。

たとえば、

foo.tar.gz → foo.tar-v1.gz

なのか、

foo-v1.tar.gz

なのか。

さらに、

.gitignore
README.
foo..md

などもあります。

Primitive IOの用途なら、Outputを .md / .txt に限定するのもかなり合理的です。Input MVPもmd/txt限定でしたし、「会話要約を保存する」という用途なら、むしろ自由な拡張子を許可するメリットが小さいです。

個人的には、

ベース名だけ入力 → 出力形式を Markdown / Text から選択

くらいでもいいと思います。

2. バージョン判定の「完全一致」は大文字小文字を明記した方がいい

Dropboxのパス自体はcase-insensitiveです。

ところが仕様には、

ベースstem-v<number>extension と完全一致

とあります。

例えば、

Memo.md
memo-v1.md

をどう扱うか。

Primitive IO側がcase-sensitiveに比較すると、Dropbox上では衝突する可能性があります。

したがって、ここは少なくとも、

Dropboxの名前衝突規則に合わせ、バージョン探索時のファイル名比較は大文字小文字を区別しない。

としておいた方が安全です。

これは実装バグになりやすいところです。

3. v01 / v001 をどうするか

現在の、

-v に続く0以上の整数

だと、

memo-v01.md

もバージョン1として認識するように読めます。

すると、

memo-v1.md
memo-v01.md

が同じバージョン番号になります。

致命的ではありませんが、仕様として、

-v0|[1-9][0-9]*

のように先頭ゼロは禁止して、既存の v01 は別命名形式として無視する方が単純です。

4. 「Dropbox更新」で何を破棄するのかが少し強すぎる

6.2では、

Dropbox更新、接続解除、ページ再読込・遷移は、アクティブフォルダ・計算済みファイル名・候補を 未選択 へ戻す。

となっています。

Cloud Explorerの「更新」を押すたびに保存先まで消えるなら、実際に使うとちょっと面倒そうです。

たとえば、

/project/Primitive IO を保存先にする
→ ファイルが増えたので更新
→ 保存先が解除される
→ またフォルダを探して「保存先にする」

になります。

ここは、

通常のDropbox更新
→ activeFolder IDは維持
→ パスと一覧を再取得
→ folder IDが存在しなければ解除
→ 計算済みファイル名だけ再計算

の方がUX的には自然そうです。

接続解除・ページ再読込なら全破棄でいいと思います。

5. 「保存を依頼」連打対策

これはテスト仕様に追加しておいた方がいいです。

autoSend ONで、

保存を依頼
↓
ChatGPTへ送信
↓
ユーザーがもう一回押す

となった場合、Dropbox側にファイルがまだできていなければ、再取得しても同じ v3 が出る可能性があります。

仕様上これは競合として許容していますが、同一ページ・同一操作による二重送信くらいはPrimitive IO側で防げます。

送信試行後、短時間ボタンをdisabledにするというより、

プロンプト投入または送信試行が完了したら、その操作サイクルを完了状態にする。ベース名または保存先の変更、Dropbox更新などで再度有効化する。

くらいが安全です。

これは外部競合防止ではなく、単純な誤操作防止です。

6. プロンプトに「Markdown」を明示した方がいい

たとえば 議事録-v3.md に対して、

この会話での議論内容を要約し

だけだと、ChatGPT側がどういうフォーマットを生成するか任意です。

.mdなら、

この会話での議論内容をMarkdown文書として要約し

の方が出力が安定します。

逆に .txt ならプレーンテキスト。

ここは拡張子からPrimitive IOが文面を変えるのではなく、v0.3.0をMarkdown専用にしてしまえばさらに単純になります。

7. かなり重要：Output候補の意味が少し分かりにくい

現在、

Dropbox InputでPrimitive IOの読み込みプロンプトを正常に投入したファイルは、同じページ内だけ出力名候補にする。

となっています。

これは内部仕様としては理解できますが、ユーザー視点だと、

「さっき読んだファイルの名前が、なぜ保存ファイル名候補になっているのか」

が少し不思議かもしれません。

実際には、

Primitive IO v0.3.0.md を読む
↓
議論する
↓
Output
↓
Primitive IO v0.3.0.md が候補
↓
次版を保存

というワークフローですよね。

だったらUI上は「入力候補」より、

「読み込み履歴から選択」

くらいの名前の方が意味が通じます。

それ以外はかなり良い

特に良いと思ったのが、

保存ではなく保存を依頼

という区別です。

これはPrimitive IOの責任範囲をUI上でも正確に表しています。

そして、

Primitive IO OAuth
→ metadata readのみ

Primitive IO
→ 保存先とファイル名を決める

ChatGPT
→ 会話を要約してDropbox操作を要求

ChatGPT Dropbox連携
→ 実際の書き込み

という境界が明確です。

以前のInput版が、

「ファイル本文を運ばず、どこを読ませるかだけ指定する」

だったのに対して、Output版も、

「生成内容を運ばず、どこへ何という名前で保存させるかだけ指定する」

になっています。

つまりPrimitive IOの名前どおり、

Input = read先を構造化して指定
Output = write先を構造化して指定

になってきました。

今回なら、上の 2（case-insensitive）・4（更新時の状態保持）・5（二重送信） は実装前に仕様へ入れておく価値が特に高いです。
